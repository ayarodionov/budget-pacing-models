# Elixir implementation

The pacing controller in Elixir, for a center that has no numerics library:

- **`PacingController`** ([pacing_controller.ex](pacing_controller.ex)): the
  proposed controller (Bayes estimate of k, even pacing, risk budget ε) as a pure
  functional state machine for one campaign. It gives bit-identical decisions to
  the Python reference `BayesRiskController`.
- The special functions it needs (ln Γ, the regularised incomplete beta and gamma
  functions, and the two spend tails built on them), in two modules with the same
  API:

  - **`PacingMath`** ([pacing_math.ex](pacing_math.ex)): pure Elixir, uses only
    Erlang's `:math`. **Recommended.**
  - **`PacingMathNif`** ([pacing_math_nif.ex](pacing_math_nif.ex) +
    [c_src/pacing_math_nif.c](c_src/pacing_math_nif.c)): the same algorithms in C,
    as a NIF. About 14× faster, but rarely worth it (see below).

All are line-by-line ports of the Python reference (`src/pacing/controllers.py`,
`src/pacing/specfun.py`). The math is tested against scipy, and the controller
against recorded traces of the Python controller. The controller logic is
explained in [IMPLEMENTATION.md](../IMPLEMENTATION.md) and
[../models/probabilistic.md](../models/probabilistic.md).

The token caps ([../models/token-cap-a.md](../models/token-cap-a.md),
[../models/token-cap-b.md](../models/token-cap-b.md)) are not ported: they need
enforcement on the clients, and the center's side is a counter (allowance
A = B/c + F_obs − U), not a numerical algorithm.

## The controller

```elixir
c = PacingController.new(
  budget: 5000,     # B, budget units
  horizon: 3600,    # T, seconds
  delay: 30,        # d, seconds until a spend shows in the budget
  step: 5,          # Δ, control period, seconds
  prior_mean: 100,  # rough guess of k, spends per second at p = 1
  eps: 1.0e-3       # allowed overspend probability for the whole campaign
)

# every `step` seconds, from period 0 on:
{p, send?, c} = PacingController.step(c, visible_spend)
if send?, do: broadcast(p)
```

`step/2` takes the spend the budget shows now, in budget units. It keeps the
exposure bookkeeping itself: it remembers the p of every period and splits it into
the exposure whose spend is visible (E) and the exposure still in flight (W).
Call it exactly once per period, starting at t = 0. It returns:

- `p`: the token probability for the next period, in [0, 1];
- `send?`: whether to broadcast it. Always true unless `broadcast_threshold`
  is set; then false when the clients' current p is kept;
- the new state. `c.risk_used` (≤ ε), `c.broadcasts` and `c.period` can be read
  from it.

`decide(c, t, observed_spend, observed_exposure, inflight_exposure)` is the same
decision with E and W passed in, for a center that tracks exposure itself, for
example with a delay that is not a whole number of periods.

Further options: `unit_cost` (c, budget units per realised token), `endgame`
(seconds; see [IMPLEMENTATION.md](../IMPLEMENTATION.md#the-end-game)),
`broadcast_threshold`, `eta`, `eta_period`, `prior_shape`, `known_rate`,
`flat_after_data` and `math: PacingMathNif`. They match the Python controller;
the module doc lists them all.

The state is a plain struct and the functions are pure, so the controller fits
in a GenServer per campaign, and its state can be persisted and restored.

## Math API

`PacingMath` and `PacingMathNif` export the same functions. All return floats.

| Function | Meaning |
|---|---|
| `nb_tail(m, alpha, beta, exposure)` | P(X > m), where X ~ Poisson(k · exposure) and k ~ Gamma(alpha, rate beta). This is the risk check's tail of the in-flight spend |
| `poisson_tail(m, mu)` | P(X > m), X ~ Poisson(mu). Used when k is known (oracle) |
| `betainc(a, b, x)` | Regularised incomplete beta I_x(a, b) |
| `gammainc_lower(a, x)` | Regularised lower incomplete gamma P(a, x) |
| `lgamma(x)` | ln Γ(x), x > 0 |
| `log1p(x)` | ln(1 + x), accurate for small x (`PacingMath` only; `:math` has none) |

`m` is a count of spends; non-integer values are rounded down. Divide budget
amounts by the cost per spend c first (see [IMPLEMENTATION.md](../IMPLEMENTATION.md),
*Units*).

```elixir
# Risk of overspend from spend in flight. 1000 spends seen over 10 s of
# full-throttle exposure (posterior Gamma(1 + 1000, 10), k ≈ 100 spends/s),
# 0.42 s of exposure in flight (≈ 42 spends expected), 60 spends of budget left.
PacingMath.nb_tail(60, 1 + 1000, 10.0, 0.42)
#=> 0.00422553245648509
```

If an iteration does not converge (it should not happen in the controller's
range), `PacingMath` raises `ArithmeticError` and `PacingMathNif` raises
`{:error, :no_convergence}`.

## Requirements

- Elixir 1.19 / Erlang OTP 28 (older versions likely work; these are tested).
- For the NIF only: a C compiler (`cc`) and the ERTS headers, which come with
  Erlang. The Makefile finds them with `erl`.

## Build, test, benchmark

From the repository root:

```bash
make -C elixir          # build priv/pacing_math_nif.so
make -C elixir test     # math against scipy; controller against Python traces (builds the NIF first)
make -C elixir bench    # pure Elixir vs NIF speed
make -C elixir clean    # remove priv/
```

The tests run `PacingMathNif` only if it loads, so pure Elixir can be tested
without a C compiler: `elixir -r pacing_math.ex pacing_math_test.exs` from this
folder, and likewise `elixir -r pacing_math.ex -r pacing_controller.ex
pacing_controller_test.exs`. `PacingMathNif` looks for the library in `priv/` next to its source, or
at the path in the `PACING_MATH_NIF` environment variable (without the `.so`).

To regenerate the golden tests after changing the Python reference:

```bash
uv run python scripts/gen_elixir_golden.py              # math cases
uv run python scripts/gen_elixir_controller_golden.py   # controller traces
```

## Pure Elixir or the NIF?

| | pure Elixir | NIF |
|---|---|---|
| one tail evaluation | 0.8–9 µs | 0.06–0.65 µs |
| worst-case decision (~31 tail evaluations, with bisection) | 67 µs | 6 µs |
| `PacingController.step/2`, average over a campaign | 2.3 µs | 0.5 µs |

(Apple M-series, OTP 28, `make -C elixir bench`.) The average is much lower than
the worst case because the bisection runs only in the few periods where the risk
check cuts p.

Use **pure Elixir**. One campaign decides once per control period (5 s), so even
the worst case, 67 µs, is about 0.001 % of a core. The NIF pays off only with roughly 10,000 or
more campaigns deciding every second, and it brings costs: a C bug can crash
the whole node, it must be built for every target, and it is harder to review.
The modules share an API, so switching later is a one-line change. Details:
[IMPLEMENTATION.md §3](../IMPLEMENTATION.md#pure-elixir-or-a-nif).

## Using it in a Mix project

Copy `pacing_math.ex` and `pacing_controller.ex` into `lib/`. For the NIF as well, copy `pacing_math_nif.ex`
and `c_src/`, add [`elixir_make`](https://hex.pm/packages/elixir_make) to the
compilers, and point it at this Makefile. Then set `PACING_MATH_NIF` or change
`load_nif/0` to load from `:code.priv_dir(:your_app)`.
