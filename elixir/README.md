# Elixir implementation

The pacing controller in Elixir, for a center that has no numerics library:

- **`PacingController`** ([pacing_controller.ex](pacing_controller.ex)): the
  proposed controller (Bayes estimate of k, even pacing, risk budget ε) as a pure
  functional state machine for one campaign. It gives bit-identical decisions to
  the Python reference `BayesRiskController`.
- The special functions it needs (ln Γ, the regularised incomplete beta and gamma
  functions, and the two spend tails built on them), in two modules with the same
  API:

  - **`PacingMath`** ([pacing_math.ex](pacing_math.ex)): pure Elixir, uses only
    Erlang's `:math`. **Recommended.**
  - **`PacingMathNif`** ([pacing_math_nif.ex](pacing_math_nif.ex) +
    [c_src/pacing_math_nif.c](c_src/pacing_math_nif.c)): the same algorithms in C,
    as a NIF. About 14× faster, but rarely worth it (see below).
- **`TokenCap`** ([token_cap.ex](token_cap.ex)): the center's side of the token
  cap, which makes overspend impossible. `TokenCap.Reports` is version (a)
  ([../models/token-cap-a.md](../models/token-cap-a.md)), `TokenCap.Grants` is
  version (b) ([../models/token-cap-b.md](../models/token-cap-b.md)).
- **`PacingCenter`** and **`PacingClient`** ([pacing_center.ex](pacing_center.ex),
  [pacing_client.ex](pacing_client.ex)): the processes around them. The center
  runs the controller every period and broadcasts p. With a token cap it also
  registers clients and hands out tokens under leases. Clients subscribe,
  decide each bid and hold their lease. They implement
  [../models/system.md §6](../models/system.md#6-how-clients-join-subscription-and-registration).

The controller, the cap and the math are line-by-line ports of the Python reference (`src/pacing/controllers.py`,
`src/pacing/specfun.py`, `src/pacing/backstop.py`). The math is tested against
scipy, and the controller and the token cap against recorded traces of the
Python simulations. The controller logic is explained in
[implementation.md](../models/implementation.md) and
[../models/probabilistic.md](../models/probabilistic.md).

## The controller

```elixir
c = PacingController.new(
  budget: 5000,     # B, budget units
  horizon: 3600,    # T, seconds
  delay: 30,        # d, seconds until a spend shows in the budget
  step: 5,          # Δ, control period, seconds
  prior_mean: 100,  # rough guess of k, spends per second at p = 1
  eps: 1.0e-3       # allowed overspend probability for the whole campaign
)

# every `step` seconds, from period 0 on:
{p, send?, c} = PacingController.step(c, visible_spend)
if send?, do: broadcast(p)
```

`step/2` takes the spend the budget shows now, in budget units. It keeps the
exposure bookkeeping itself: it remembers the p of every period and splits it into
the exposure whose spend is visible (E) and the exposure still in flight (W).
Call it exactly once per period, starting at t = 0. It returns:

- `p`: the token probability for the next period, in [0, 1];
- `send?`: whether to broadcast it. Always true unless `broadcast_threshold`
  is set; then false when the clients' current p is kept;
- the new state. `c.risk_used` (≤ ε), `c.broadcasts` and `c.period` can be read
  from it.

`decide(c, t, observed_spend, observed_exposure, inflight_exposure)` is the same
decision with E and W passed in, for a center that tracks exposure itself, for
example with a delay that is not a whole number of periods.

Further options: `message_delay_max` (seconds before a new p is sure to reach
the clients, for a broker or clients that poll; it widens the in-flight window,
see [system.md §6](../models/system.md#push-or-pull)), `max_silence` (the
clients' silence limit in seconds; the risk check charges each p for
max(step, max_silence)), `delay_pmf` (for a spend delay that varies: the
probability that a spend shows up after 0, 1, 2, ... periods; `step/2` then
weights the exposure by it, see [system.md §7](../models/system.md#a-spend-delay-that-varies)),
`max_rise` (p may grow
by at most this factor per spend delay d; 1.5 bounds the damage of a delay
nobody planned for to about 1 % of B and costs nothing otherwise), `unit_cost` (c, budget
units per realised token), `endgame`
(seconds; see [implementation.md](../models/implementation.md#the-end-game)),
`broadcast_threshold`, `eta`, `eta_period`, `prior_shape`, `known_rate`,
`flat_after_data` and `math: PacingMathNif`. They match the Python controller;
the module doc lists them all.

The state is a plain struct and the functions are pure, so the controller fits
in a GenServer per campaign, and its state can be persisted and restored.

## The token cap

The cap is a hard limit: every bid needs a token, and the center never lets out
more tokens than the budget can pay for, floor(B/c). The controller still sets
p; the cap only blocks bids when its allowance runs out. Clients must enforce
it (no bid without a token); how tokens reach them (a shared pool, wallets,
leases) is up to the application.

**Version (a), `TokenCap.Reports`: clients report used tokens and failures.**
Safe whatever the delay.

```elixir
cap = TokenCap.Reports.new(budget: 5000)            # unit_cost: c, default 1

# every period, after PacingController.step/2 returned p:
a = TokenCap.Reports.allowance(cap)                 # max(B/c + F_obs − U, 0) tokens
# ... clients bid with p, using at most `a` tokens; they report back:
cap = TokenCap.Reports.record_use(cap, used)
cap = TokenCap.Reports.record_failures(cap, failed) # bids that were not charged
ctl = PacingController.correct_exposure(ctl, TokenCap.Reports.effective_p(p, used, wanted))
```

`correct_exposure/2` tells the controller that only `used` of the `wanted` bids
were made. Without it, blocked bids would look like a lower k, and pacing would
push p up.

**Version (b), `TokenCap.Grants`: clients report nothing.** Each period's grant
expires at its end. Safe only if the delay d is a hard maximum.

```elixir
cap = TokenCap.Grants.new(budget: 5000, delay: 30, step: 5, share: 0.5)

# every period:
{grant, cap} = TokenCap.Grants.grant(cap, visible_spend)
# ... send p and `grant` tokens, valid for this period only
```

The grant is at most A = floor(B/c) − S_obs/c − (tokens granted in the last d
seconds). `share: s` grants ⌈s·A⌉ (0.5 recommended); `headroom: h` grants
⌈h·λ·p·Δ⌉ instead, with the expected bids λ·p·Δ passed as
`grant(cap, spend, expected_bids: ...)`.

## Registration (`PacingCenter` and `PacingClient`)

One `PacingCenter` per campaign, and one `PacingClient` per bidder. The center
runs a step every `step_ms`: it reads the visible spend, asks the controller for
p, broadcasts it, and in version (b) sends each live lease its share of the
grant.

```elixir
{:ok, center} =
  PacingCenter.start_link(
    campaign: :summer,
    mode: :reports,                        # :broadcast | :reports (cap a) | :grants (cap b)
    controller: [budget: 5000, horizon: 3600, delay: 30, step: 5, prior_mean: 100, eps: 1.0e-3],
    cap: [budget: 5000],                   # TokenCap options; not used in :broadcast mode
    visible_spend: fn -> Budget.visible_spend(:summer) end,
    step_ms: 5_000,
    authenticate: fn client_id, credentials -> MyAuth.valid?(client_id, credentials) end
  )

{:ok, client} =
  PacingClient.start_link(center: center, campaign: :summer,
                          client_id: "bidder-7", credentials: token, wallet_size: 10)

# in each bidding process, once:
h = PacingClient.handle(client)
# for every bid request:
if PacingClient.bid?(h), do: place_bid()
# :reports mode, when a bid turns out not to be charged:
PacingClient.report_failure(h)
```

What each mode does:

| Mode | Client joins by | Tokens | Client reports |
|---|---|---|---|
| `:broadcast` | subscribing (no registration) | none | nothing |
| `:reports` | registering; heartbeats keep the lease | wallet of `wallet_size`, topped up from the center | failed bids, with heartbeats and top-ups |
| `:grants` | registering; heartbeats keep the lease | the period's grant, split evenly among live leases | nothing |

The safety rules of §6 are built in:

- **Client side**, checked at every `bid?/1` against the client's own clock:
  - p counts as 0 after `silence_ms` without a message (default 3 periods);
  - messages are applied only if `{epoch, seq}` is newer;
  - a wallet is usable only until the lease runs out without renewal; then the
    client registers again and reports the old lease;
  - a grant is usable only for `valid_ms` after it arrives.
- **Center side**:
  - only authenticated clients register;
  - a lost lease keeps its tokens counted until the client settles it;
  - credits per lease never exceed the tokens it was handed.

**Fast path.** `PacingClient.bid?/1` with a `PacingClient.Handle` sends no
message. The client keeps the latest `{epoch, seq, p, heard_at}` in an ETS row
and its tokens and their validity in `:atomics`. The bidding process reads these
directly and takes a token with compare-and-swap, so any number of processes can
bid at once and a token is never taken twice. The client process is called only
when a `:reports` wallet is empty (top-up) or the lease has run out (register
again): about once per `wallet_size` bids. When a top-up gets nothing (budget
used up), bids are refused without calls until the next heartbeat or one period
later. `bid?/1` with the client's pid still works, with one call per bid.

**Relay (the hybrid of [§6](../models/system.md#push-or-pull)).** With many
clients on a node, start one `PacingRelay` per node and campaign. It subscribes
once and writes p to a named ETS table; clients started with `relay: table` read
p from there and do not subscribe themselves:

```elixir
{:ok, _} = PacingRelay.start_link(center: center, campaign: :summer, table: :summer_p)
{:ok, c} = PacingClient.start_link(center: center, campaign: :summer, relay: :summer_p, ...)
```

The center then sends one message per node per period instead of one per client.
The relay keeps no state of its own and writes only newer messages. If it dies,
its table goes with it, clients read no p and stop bidding (safe); restart it
under a supervisor.

**Delivery delay (δ_max).** If p or grants can reach clients late (a broker, a
relay, clients that poll), give the center the largest delay:

```elixir
PacingCenter.start_link(..., step_ms: 5_000, message_delay_max_ms: 1_000)
```

This one setting keeps the parts consistent:
- the controller's in-flight window grows by ceil(δ_max / step) periods;
- in `:grants` mode the grant margin defaults to δ_max. A smaller margin is
  refused at start, and so is a δ_max of a whole period or more;
- clients learn it from `hello/1` and wait 3 periods plus δ_max before treating
  silence as a stop.

The center also refuses a controller or cap whose `step` (seconds) differs from
`step_ms`, and a controller `message_delay_max` that contradicts
`message_delay_max_ms`. Ignoring a real delay breaks the guarantees
([system.md §6](../models/system.md#push-or-pull)).

**When the delay is far larger than planned.** A backlog of minutes makes the
controller mistake "no spend yet" for "low k" and push p to 1; in the
simulations that spends about 3 × B. Two defences are built in, plus the
controller's `max_rise`:

- **Age check (clients and relay).** Every message carries `sent_at`, the
  center's wall-clock time. A client or relay drops a message older than
  `max_age_ms` (from `hello/1`: δ_max + `clock_skew_ms`, default skew 1 s), so a
  steady stream of late messages ends in a stop by silence. Needs clocks
  synchronised within the skew; `max_age_ms: :infinity` turns it off.
- **Halt on measured delay (center, token-cap modes).** Clients send the
  `{epoch, seq}` they applied last with every heartbeat and top-up. The center
  knows when it sent each `seq`, so it bounds the delay from below using only
  its own clock. Above `message_delay_max_ms + lag_allowance_ms` (default one
  period) it *halts*: it sends p = 0 and grants nothing, and calls
  `on_alarm.({:lag, client_id, lag_ms})` (default: log an error).
  `PacingCenter.resume/1` ends the halt.

Messages are now `{:pacing_p, campaign, epoch, seq, p, sent_at}`,
`{:pacing_keepalive, campaign, epoch, seq, sent_at}` and
`{:pacing_grant, campaign, epoch, seq, tokens, valid_ms, sent_at}`.

**Outages: lost connection, stalled budget feed, restart**
([system.md §6](../models/system.md#push-or-pull)):

- **Durable state.** `store: {PacingCenter.FileStore, path}` (or any module with
  the `PacingCenter.Store` callbacks `load/1` and `save/2`). Token counts,
  leases, the grant window, the controller state and a halt are written
  *before* tokens, grants or p leave the center. A restarted center loads them
  and starts a new epoch; clients carry on with their old leases. Without a
  store, a restart forgets the tokens it handed out and hands the budget out
  again (there is a test showing exactly that).
- **Budget feed freshness.** `visible_spend` may return `{spend, as_of_ms}`
  (wall clock). If the spend is older than `spend_delay_ms` (default: the
  controller's `delay`) + `feed_tolerance_ms` (default 2 periods), the center
  halts: p = 0, no grants, `on_alarm.({:stale_budget, age_ms})`. It resumes by
  itself when the feed is fresh again. A feed that returns a bare number is
  never checked.
- **The controller counts the p actually sent.** While halted, the center calls
  `PacingController.correct_exposure(ctl, 0.0)`, so the exposure does not grow
  with nothing spent and the estimate of k stays unbiased.
- **Planning for a lost link.** By default the center sets the controller's
  `max_silence` to the clients' silence limit (3 periods + δ_max), so each p is
  charged as if it may run that long. `plan_for_lost_link: false` turns it off.
  Clients must not use a longer `silence_ms` than the center assumes.
- **Shrinking wallets.** A top-up gives at most `wallet_share` (0.5) × the
  remaining allowance / the number of live leases, so near the end a cut-off
  client holds back little budget.

Clients find the center's p channel through the `:pg` group
`{:pacing, campaign}`. `:pg` works on one node and across a cluster. Start the
scope `PacingCenter.PG` in your supervision tree (`PacingCenter.subscribe/2`
starts it on demand otherwise).

Tests use `tick: :manual`, a fake `:clock` and a fixed `:coin`, which make every
step deterministic. In production leave the defaults: real timers, monotonic
time and `:rand`.

Not wired in yet: in `:reports` mode the center does not pass blocked bids to
`PacingController.correct_exposure/2`. Clients count them (`wanted` vs `bids`
in `PacingClient.info/1`), but the counts are not reported per period. Until they
are, the estimate of k can drift low when the cap blocks many bids. That happens
mostly near the end of the campaign, when the cap binds.

## Math API

`PacingMath` and `PacingMathNif` export the same functions. All return floats.

| Function | Meaning |
|---|---|
| `nb_tail(m, alpha, beta, exposure)` | P(X > m), where X ~ Poisson(k · exposure) and k ~ Gamma(alpha, rate beta). This is the risk check's tail of the in-flight spend |
| `poisson_tail(m, mu)` | P(X > m), X ~ Poisson(mu). Used when k is known (oracle) |
| `betainc(a, b, x)` | Regularised incomplete beta I_x(a, b) |
| `gammainc_lower(a, x)` | Regularised lower incomplete gamma P(a, x) |
| `lgamma(x)` | ln Γ(x), x > 0 |
| `log1p(x)` | ln(1 + x), accurate for small x (`PacingMath` only; `:math` has none) |

`m` is a count of spends; non-integer values are rounded down. Divide budget
amounts by the cost per spend c first (see [implementation.md](../models/implementation.md),
*Units*).

```elixir
# Risk of overspend from spend in flight. 1000 spends seen over 10 s of
# full-throttle exposure (posterior Gamma(1 + 1000, 10), k ≈ 100 spends/s),
# 0.42 s of exposure in flight (≈ 42 spends expected), 60 spends of budget left.
PacingMath.nb_tail(60, 1 + 1000, 10.0, 0.42)
#=> 0.00422553245648509
```

If an iteration does not converge (it should not happen in the controller's
range), `PacingMath` raises `ArithmeticError` and `PacingMathNif` raises
`{:error, :no_convergence}`.

## Requirements

- Elixir 1.19 / Erlang OTP 28 (older versions likely work; these are tested).
- For the NIF only: a C compiler (`cc`) and the ERTS headers, which come with
  Erlang. The Makefile finds them with `erl`.

## Build, test, benchmark

From the repository root:

```bash
make -C elixir          # build priv/pacing_math_nif.so
make -C elixir test     # math against scipy; controller and token cap against Python traces;
                        # registration and leases (builds the NIF first)
make -C elixir bench    # pure Elixir vs NIF speed
make -C elixir clean    # remove priv/
```

The tests run `PacingMathNif` only if it loads, so pure Elixir can be tested
without a C compiler: `elixir -r pacing_math.ex pacing_math_test.exs` from this
folder, and likewise `elixir -r pacing_math.ex -r pacing_controller.ex
-r token_cap.ex token_cap_test.exs` (and the same for
`pacing_controller_test.exs`; add `-r pacing_center.ex -r pacing_client.ex` for
`registration_test.exs`). `PacingMathNif` looks for the library in `priv/`
next to its source, or at the path in the `PACING_MATH_NIF` environment variable
(without the `.so`).

To regenerate the golden tests after changing the Python reference:

```bash
uv run python scripts/gen_elixir_golden.py              # math cases
uv run python scripts/gen_elixir_controller_golden.py   # controller traces
uv run python scripts/gen_elixir_token_cap_golden.py    # token-cap traces
(cd elixir && mix format pacing_math_test.exs)          # the math test is generated unformatted
```

## Pure Elixir or the NIF?

| | pure Elixir | NIF |
|---|---|---|
| one tail evaluation | 0.8–9 µs | 0.06–0.65 µs |
| worst-case decision (~31 tail evaluations, with bisection) | 67 µs | 6 µs |
| `PacingController.step/2`, average over a campaign | 2.3 µs | 0.5 µs |

And the per-bid cost of `PacingClient.bid?/1` (pure Elixir; `make -C elixir bench`):

| | through the client process (pid) | fast path (`Handle`) |
|---|---|---|
| one bidder, per bid | 825 ns | 107 ns |
| 10 bidders at once | about 1 million bids/s (they queue on one process) | about 30 million bids/s |

(Apple M-series, OTP 28, `make -C elixir bench`.) The average is much lower than
the worst case because the bisection runs only in the few periods where the risk
check cuts p.

Use **pure Elixir**. One campaign decides once per control period (5 s), so even
the worst case, 67 µs, is about 0.001 % of a core. The NIF pays off only with roughly 10,000 or
more campaigns deciding every second, and it brings costs: a C bug can crash
the whole node, it must be built for every target, and it is harder to review.
The modules share an API, so switching later is a one-line change. Details:
[implementation.md §3](../models/implementation.md#pure-elixir-or-a-nif).

## Using it in a Mix project

Copy `pacing_math.ex`, `pacing_controller.ex`, `token_cap.ex`,
`pacing_center.ex` and `pacing_client.ex` into `lib/`, and start `{:pg,
PacingCenter.PG}` (as `%{id: :pg, start: {:pg, :start_link, [PacingCenter.PG]}}`)
in the application's supervision tree. For the NIF as well, copy `pacing_math_nif.ex`
and `c_src/`, add [`elixir_make`](https://hex.pm/packages/elixir_make) to the
compilers, and point it at this Makefile. Then set `PACING_MATH_NIF` or change
`load_nif/0` to load from `:code.priv_dir(:your_app)`.
